# LLM.md — universal agent context

Agent-agnostic project context. Read this before changing anything. Update it when architecture or decisions change, not just when code changes.

## Instructions for any coding agent working here

- **Always update this file** when you change architecture, a decision, or a gotcha — not just when you change code. A future agent (any vendor, not just Claude) should be able to read this file alone and not rediscover what's already been learned.
- This repo is public — no company-specific hostnames, internal URLs, or org names in code, docs, or commit messages. If you spot one that slipped in, flag it and ask before scrubbing it yourself.
- Don't reintroduce hardcoded hosts (`content_scripts`/`host_permissions` in `manifest.json`) — see "Permissions model" below for why, and keep new features on the runtime-request flow.
- The ArgoCD DOM/API assumptions here (class names, `title` format, `resource-tree` endpoint shape) came from reading `argoproj/argo-cd`'s public UI source, not from live inspection — this project has no browser automation against a real (IAP-gated) ArgoCD instance. If something stops matching after an ArgoCD upgrade, re-derive it from that source rather than guessing, and update this file with what changed.
- No build step, no automated tests — verify changes by loading the repo unpacked in `chrome://extensions` (see Testing below) before calling anything done.

## What this is

Chrome extension (Manifest V3), public (not tied to any one company — no hardcoded hosts). Fixes/extends ArgoCD's own UI, starting with: filter the Application resource tree by object kind (Deployment / Service / ConfigMap), hiding everything else while keeping the selected kind's descendants (ReplicaSet, Pod, etc.) — unlike ArgoCD's native "Kind" filter, which filters every node independently and breaks the tree (hides children too). Also lets the user permanently hide low-signal kinds (e.g. Secret) by default, editable from an options page or a "Hide by default" item injected into ArgoCD's own node kebab menu. Separately, ReplicaSets with no descendants (old, scaled-down revisions) are hidden by default too, also toggleable from the options page.

Filtering happens at the **data** layer, not the DOM: `page-interceptor.js` rewrites ArgoCD's own resource-tree API responses before React ever sees the dropped nodes, so ArgoCD's own dagre layout renders an already-pruned graph — no hidden-but-still-laid-out nodes, no gaps, no DOM surgery. See "Graph-level filtering" below for why, and for the DOM-hiding approach this replaced (kept around on the `compaction-shift` branch as a reference of what *not* to do).

## File map

- `manifest.json` — MV3 manifest. No `content_scripts`/`host_permissions` — injection is fully dynamic (see Permissions model below).
- `page-interceptor.js` — runs in the page's own **MAIN world** (see Permissions model / Graph-level filtering below), patches `window.EventSource` to filter ArgoCD's resource-tree stream before React sees it.
- `content.js` / `content.css` — runs in the isolated content-script world: renders the floating draggable "Kind filter" widget, tracks the selected kind + hidden-by-default kinds, and tells `page-interceptor.js` about them via `postMessage` (the two worlds share the DOM but not JS globals — no other way to talk to each other). Also injects the "Hide by default" kebab-menu item.
- `options.html` / `options.js` / `options.css` — extension options page (`options_ui`, opens in a tab): edit the global "hidden by default" kinds list.
- `popup.html` / `popup.js` / `popup.css` — toolbar popup: lets the user add/remove ArgoCD hosts, requests permission per host, registers/injects both scripts.
- `background.js` — MV3 service worker. Only job: reconcile dynamic content-script registration with actually-granted permissions on `onInstalled`/`onStartup`.
- `shared.js` — ES module shared between `background.js` and `popup.js` (host normalization, `chrome.storage` helpers, `chrome.scripting.registerContentScripts` wrapper — registers *both* `content.js` and `page-interceptor.js`). Both load it via `type: "module"`.
- `icons/icon.svg` + rasterized `icons/icon{16,32,48,128}.png` — toolbar/store icon (funnel + colored dots = "filter by kind"). Regenerate PNGs from the SVG with `rsvg-convert -w <size> -h <size> icon.svg -o icon<size>.png` if the design changes.

## Permissions model — why there's no hardcoded host

This started as a internal tool with hosts hardcoded in `manifest.json`. To make it public, switched to:

- `optional_host_permissions: ["https://*/*"]` in the manifest (broad *declaration*, required so the runtime request below is even possible).
- Popup calls `chrome.permissions.request({origins: ["https://<host>/*"]})` for the *specific* host the user types — Chrome shows a native prompt scoped to that one host, not the wildcard.
- On grant: host saved to `chrome.storage.local`, `chrome.scripting.registerContentScripts()` registers **two** scripts for that host (persists across restarts) — `content.js`/`content.css` (isolated world, `document_idle`) and `page-interceptor.js` (**MAIN world**, `document_start` — see "Graph-level filtering" below for why it needs the page's own JS realm and to run that early). `chrome.scripting.executeScript`/`insertCSS` also inject both into the *currently open* tab immediately (registration alone only affects future page loads) — though for the MAIN-world script that immediate injection is necessarily best-effort: if ArgoCD's bundle already opened its resource-tree stream before the user clicked "Enable", that specific connection won't be filtered until the next reload.
- Remove flow: `chrome.permissions.remove()` + drop from storage + re-register.
- `background.js` reconciles on startup/install in case Chrome drops a registration or a permission gets revoked outside the popup (e.g. via `chrome://extensions`).

**Gotcha: `chrome.scripting.registerContentScripts()` is all-or-nothing.** If *any* id in the call is already registered, the whole call throws and registers *none* of the scripts, not just the conflicting one. `reconcileContentScripts()` runs on every host add/remove and on every `onInstalled`/`onStartup`, so hitting an already-registered id is the normal case, not an edge case — a reload or reinstall is enough to trigger it. `shared.js` handles this by checking `chrome.scripting.getRegisteredContentScripts()` first and routing each script to `registerContentScripts` (new) or `updateContentScripts` (already registered) accordingly, rather than blindly unregistering-then-registering. `popup.js` also now wraps both `addHost`/`removeHost`'s reconcile calls and shows the error via the existing `errorMsg` element instead of letting it silently abort the handler; `background.js` at least logs it. This is a real, still-worthwhile hardening fix, but turned out **not** to be the cause the one time this was actually chased down (see next gotcha) — don't assume it's the whole story if "Enable" misbehaves again.

**Gotcha: the "Enable on this site" one-click button needs `activeTab` to see the current tab's URL at all.** `popup.js`'s `init()` calls `chrome.tabs.query({active:true, currentWindow:true})` and reads `tab.url` to compute `activeTabHost` — but without the `activeTab` permission (or without *already* holding host permission for that tab's origin from some earlier grant), Chrome returns the tab object with `url` stripped/undefined. `activeTabHost` then ends up `null`, so `enableCurrentBtn`'s click handler (`if (activeTabHost) addHost(activeTabHost)`) just silently no-ops — no error thrown anywhere, because `addHost()` is never even called. Symptom: the button looks completely normal, does nothing on click, no console output anywhere (popup, service worker, or the ArgoCD page) — while manually typing the same host into the add-host input works fine, since that path never touches `tab.url`. This is why it went unnoticed for a while: it only reproduces on a *fresh* install/permission-wipe, since once a host is granted once, `tab.url` becomes visible for that origin from then on regardless of `activeTab`. Fixed by adding `"activeTab"` to `manifest.json`'s `permissions` (a silent, no-prompt permission Chrome grants for the tab that triggered the current extension UI action — exactly the popup-open gesture here).

Don't revert to static `content_scripts`/`host_permissions` — that's what made this internal-only.

## Graph-level filtering (why `page-interceptor.js` exists, and what it replaced)

The first version of this extension filtered by hiding already-rendered DOM: find `.application-resource-tree__node` elements that don't match, `display:none` them, then hide connector lines whose bounding box touched a hidden node. It worked, but ArgoCD's tree is laid out by dagre as **static absolute-pixel coordinates that don't reflow** — hiding a node doesn't shift anything else to fill the gap, so switching filters (or hiding a kind by default) left a blank hole in the canvas, and lines between two still-*visible* nodes could end up visibly crossing straight through where a hidden node used to be. Chasing that with more DOM math (scroll-to-first-visible, then a from-scratch node/edge compaction engine reverse-engineering dagre's coordinate system from ArgoCD's inline styles) got the gaps closed, but needed a second, harder pass just to keep the connector lines attached to the nodes they'd just moved — real, working, but fragile, and entirely reinvented from nothing every time the DOM changed. That whole approach is preserved on the `compaction-shift` branch as a documented dead end, not deleted, in case this rewrite doesn't hold up either.

The fix that actually addresses the root cause: **filter the graph data before dagre ever lays it out**, so dagre computes fresh, gap-free positions for the pruned graph itself — the same way it would if those nodes had simply never existed. No DOM hiding, no coordinate-space archaeology, no compaction math, and it's immune to ArgoCD DOM/CSS changes (it only depends on the API response *shape*, a far more stable contract than internal class names).

- **ArgoCD doesn't fetch the tree once — it streams it.** Reverse-engineered from `argoproj/argo-cd`'s `ui/src/app/shared/services/applications-service.ts` and `requests.ts` (not from live inspection): `watchResourceTree()` opens a native `EventSource` to `/api/v1/stream/applications/<name>/resource-tree?appNamespace=<ns>`, and each SSE message's `data` is `JSON.stringify({result: ApplicationTree, ...})` — the consumer does `JSON.parse(data).result`. There's *also* a one-shot `GET /api/v1/applications/<name>/resource-tree` (`resourceTree()`, via `superagent`, which uses XHR in the browser, not `fetch`) used as a fallback value shown immediately while the stream connects. `application-details.tsx`'s `loadAppInfo` merges *both* into the same `combineLatest` feeding the rendered tree — whichever emits most recently wins.
- **Only the `EventSource` stream is intercepted (`page-interceptor.js`), not the one-shot GET.** It overwrites `window.EventSource` with a wrapper: for any URL that doesn't match the resource-tree stream, it returns the real native instance untouched (so ArgoCD's *other* `EventSource` usage — logs, other watches — is completely unaffected); for a match, it wraps the real instance in a `Proxy` that intercepts `.onmessage`/`addEventListener('message', ...)` and rewrites each message's parsed `result` tree through `filterTree()` before handing it to ArgoCD's own handler. **Known, accepted gap:** the one-shot GET is *not* intercepted (would need overriding `XMLHttpRequest.prototype.responseText`/`.response` at the prototype level via `Object.defineProperty`, since `superagent` reads the response from whatever XHR instance it created, on its own timing we don't control — a lot more moving parts, and higher-risk than net wrapping). See the next bullet for why this turned out to matter more than expected, and how it's worked around instead of by intercepting the GET.
- **The stream doesn't push its current state just because something subscribed — confirmed live, not a flash.** The original assumption here was that the unfiltered one-shot GET result would show *briefly* before the first (filtered) stream message corrected it. In practice, ArgoCD's resource-tree watch only pushes a message when the backend actually refreshes/reconciles the app — a fresh `EventSource` subscription with nothing else happening can sit silent indefinitely, leaving the unfiltered GET result on screen until the user manually clicks ArgoCD's own "Refresh" button (`GET /api/v1/applications/<name>?appNamespace=<ns>&refresh=normal` — that request itself isn't intercepted either, it's not a resource-tree call, it just causes the backend to push one). Rather than take on XHR interception after all, `content.js`'s `triggerRefresh()` just fires that same request itself — once at startup and again on every app switch (href-poll, same pattern as the old `onAppMaybeChanged`) — forcing the stream to push promptly instead of waiting on the user to find the button. `page-interceptor.js` doesn't need to know this is happening; the forced push arrives as an ordinary stream message like any other.
- **`filterTree(tree)`** operates on the exact same `{nodes, orphanedNodes}` shape the old DOM-based version's `computeKeepSet` used, just applied to the raw API object instead of the DOM: build a `kind|namespace|name` key per node (same `nodeKey()` used everywhere else in this codebase), a `childrenByParentKey` map from `parentRefs`, and a `keep` set (kind filter's target kind + everything reachable through `childrenByParentKey`, i.e. "descendants"). A node is dropped if it fails the keep set (kind filter active and not in it) or its kind is in the hidden-by-default list (unless it's the exact kind currently selected in the filter — otherwise a hidden-by-default kind could never be looked at again).
- **Rewiring parentRefs is the one thing the DOM approach structurally couldn't do.** When a dropped node has children that survive (e.g. hiding `ReplicaSet` by default, but its `Pod`s stay), those children's `parentRefs` get rewritten to point at the nearest surviving ancestor (walking up through however many consecutively-dropped ancestors) instead of a removed node — so dagre draws a fresh edge straight from e.g. `Deployment` to `Pod`. The old DOM version couldn't do this at all: both of the removed node's edges (in-edge and out-edge) just got hidden outright, leaving the child fully disconnected with no line at all. This is a genuine capability improvement, not just a reimplementation.
- **Instant re-filtering on a client-side config change, without waiting for the server to push again.** Each intercepted stream caches the last raw (unfiltered) parsed payload (`lastParsed`). `content.js` posts `{source:"argocd-ext", type:"filter-config", selectedKind, hiddenKinds}` via `window.postMessage(..., location.origin)` any time the kind dropdown changes, a custom kind is removed while selected, or the hidden-by-default list changes (including via the options page, relayed through `chrome.storage.onChanged` — that listener fires for the writer too, not just other contexts) — `page-interceptor.js` listens for that message (filtering by `event.source === window` and a private `source` marker) and, on receipt, re-runs `filterTree()` on every open stream's *cached* `lastParsed` and re-dispatches, without needing a genuinely new server push. **This is why `postMessage` exists at all**: MAIN-world and isolated-world content scripts share the page's DOM but are separate JS realms with no shared variables and no direct function-call path — `postMessage` (received via a `window` "message" listener) is the only bridge.
- **`content.js` no longer fetches or holds the tree itself.** The old `fetchTree`/`buildChildrenMap`/`collectDescendants`/`computeKeepSet`/`treeData` are all gone from this branch — that data now only exists inside `page-interceptor.js`, arriving as a side effect of the same stream ArgoCD itself already opens. `content.js`'s job shrank to: render the widget, track `selectedKind`/`customKinds`/`hiddenKinds`, and notify the interceptor when any of them change.
- **Verified live** — this architecture (stream interception, parentRefs rewiring, instant re-filter on config change) works against a real ArgoCD instance, not just in theory.
- **Childless ReplicaSets are hidden by default** (`hideChildlessReplicaSets`, `argocd-ext-hide-childless-replicasets` in `chrome.storage.local`, global, default `true` when unset). A ReplicaSet with zero descendants in the raw tree (checked against `childrenByParent` built from *all* nodes, before any other filtering is applied — so a ReplicaSet whose Pods were merely hidden by the kind filter or hidden-by-default kinds still counts as "has descendants" and stays visible) is almost always an old, scaled-down revision ArgoCD keeps for rollback history, not something currently running. Same "unless explicitly selected" exception as hidden-by-default kinds: selecting `ReplicaSet` in the widget's kind dropdown shows every ReplicaSet regardless of this setting. Toggle lives on the options page; threaded through `filterConfig`/`postMessage` the same way as `hiddenKinds`.
- **"Show hidden-by-default kinds" checkbox** in the widget (`ignoreHiddenDefaults`, `argocd-ext-kf-ignore-hidden` in `localStorage`, per-origin like position/collapsed) is a per-instance override that tells `filterTree()` to treat the hidden-by-default list as empty for that pass, *without* touching the persisted list itself (`chrome.storage.local`) — flip it back off and the same hidden kinds are still configured. Threaded through `filterConfig` alongside `selectedKind`/`hiddenKinds`.
- **Debug logging** (`argocd-ext-debug-logging` in `chrome.storage.local`, global, off by default) gates every `[argocd-ui-enhancer]` diagnostic `console.log` in both `content.js` and `page-interceptor.js` behind a `log()` helper that checks it — real errors (`console.error`, e.g. a `filterTree()` exception) stay unconditional. Toggle lives on the options page. Since `page-interceptor.js` (MAIN world) can't read `chrome.storage` itself, its copy of the flag arrives the same way `selectedKind`/`hiddenKinds` do — as one more field on the `postMessage`d `filterConfig` — meaning its very first "installed" log line unavoidably fires *before* any config has arrived (default `false`), so that one specific line never shows even with logging enabled from a previous session; every subsequent line respects the live setting correctly.

## Widget UI

Floating panel, dark header = drag handle, ▾/▸ collapses to just the header. Position and collapsed state persist in `localStorage` (per-origin, so per ArgoCD instance) — not `chrome.storage`, since it's purely a per-page UI preference with no cross-device need.

## Current scope / known limitations

- Kind dropdown is single-select. Hardcoded base list: `All / Deployment / Service / ConfigMap / StatefulSet` (`KINDS` const in `content.js`). Users can add their own kinds (any string matching a k8s `Kind`, e.g. `Job`, `CronJob`) via a small input+list under the dropdown in the widget — stored in `localStorage` (`argocd-ext-kf-custom-kinds`, per-origin, merged with `KINDS` at render time via `getAllKinds()`). Multi-select is a natural next step, not built yet.
- Hidden-by-default kinds (`argocd-ext-hidden-kinds` in `chrome.storage.local`, global across all ArgoCD hosts) are managed from the options page (`options.html`, right-click the extension icon → Options, or `chrome://extensions`) or via a "Hide `<Kind>` by default" item injected into ArgoCD's own per-node kebab menu — see the kebab-menu DOM mechanics note below.
- **The kebab-menu injection is still DOM-based** (unrelated to the graph-filtering rewrite — it's about adding a menu item to ArgoCD's own UI, not about filtering tree data). ArgoCD's per-node kebab menu (`.application-resource-tree__node-menu`) wraps an `argo-ui` `DropDown` whose content renders into a React portal on `document.body` (`ReactDOM.createPortal`), not nested under the node — so there's no DOM ancestry from the open menu back to the node it belongs to. `content.js` captures which node's kebab was clicked via a capture-phase `document` click listener (`trackMenuNodeOnClick`, runs before ArgoCD's own handler can call `stopPropagation()`) and, since the menu's `<ul>` populates asynchronously (`DataLoader` + an Observable), watches for it via a `MutationObserver` (`injectHideByDefaultMenuItem`), appending one more `<li class="application-details__action-menu">` once the real items have loaded. Only covers the two node-menu render paths using that wrapper class (normal + "compact"/collapsed node view) — the pod-group icon view's per-pod kebab (a separate `DropDown` without that wrapper) isn't covered, acceptably rare.
- **One-shot GET fallback isn't intercepted** — see "Graph-level filtering" above. Worked around via `triggerRefresh()` forcing a stream push instead, rather than intercepting the GET itself.
- No automated tests. No browser automation access to an authenticated ArgoCD instance for the *coding agent* — all ArgoCD API/DOM assumptions above were derived by reading the public `argo-cd`/`argo-ui` source (pinned to specific files named above), not by inspecting a live page. This branch's `page-interceptor.js`/`content.js` rewrite *has* since been verified live by a human against a real instance and works. If ArgoCD upgrades change the stream's URL/payload shape, the kebab-menu DOM structure, or switch off `EventSource` entirely (e.g. to `fetch`-based SSE), this breaks silently — re-derive from source rather than guessing, the way everything above was derived.

## Testing

No build step — load unpacked: `chrome://extensions` → Developer mode → Load unpacked → repo root. Then use the toolbar popup to add a host. **Reload the ArgoCD tab once after enabling** — `page-interceptor.js` only filters `EventSource` connections opened *after* it's installed, and the popup's immediate injection can't retroactively fix a stream that was already open when you clicked "Enable" (see "Graph-level filtering" above). If the tree doesn't filter after that, check the console for `[argocd-ui-enhancer]` errors (rare — a filter failure inside `page-interceptor.js` falls back to passing the tree through unfiltered rather than throwing) and confirm `page-interceptor.js` actually registered as a MAIN-world script (`chrome://extensions` → service worker inspect, or check for it in the page's own sources panel — it runs in the page's realm, not the extension's).
